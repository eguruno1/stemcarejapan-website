# 상담채팅시스템 운영 및 유지보수 가이드

> 대상 독자: 이 프로젝트를 처음 맡는 주니어 개발자, 그리고 서버를 직접 운영해야 하는 시스템 관리자.
> "왜 이렇게 되어 있는지"를 함께 적어서, 코드를 고칠 때 실수로 규칙을 깨지 않도록 돕는 문서다.
>
> 이 문서는 기존 운영 문서(`README-chat.md`, `deploy/DEPLOY.md`, `deploy/RUNBOOK.md`, `CHECKLIST.md`,
> `apps/api/API.md`)를 대체하지 않는다. 그 문서들은 "정확한 명령어"를 담은 원본이고, 이 문서는
> 처음 보는 사람이 전체 그림을 이해하도록 돕는 안내서다. 세부 절차는 항상 원본 문서를 따른다.

## 1. 이 시스템은 무엇인가

StemCareJapan 홈페이지에는 우측 하단에 "무료 상담 채팅" 버튼이 있다. 방문자가 이름·연락처를
남기고 채팅을 시작하면:

1. AI가 먼저 응대한다 (공항 픽업 시간 같은 일반적인 질문에 답한다).
2. 가격 문의, 예약 요청, 건강 상태 언급처럼 AI가 답하면 안 되는 내용이면 자동으로
   **담당자 연결 대기** 상태로 바뀐다.
3. 담당자(운영자)가 별도의 관리자 화면에서 로그인해 상담을 이어받는다.
4. 고객이 일본어로 쓰면 운영자 화면에는 한국어 번역이 붙고, 운영자가 한국어로 답하면
   고객 화면에는 일본어 번역만 보인다. 서로 상대방 언어를 몰라도 대화가 가능하다.
5. 상담이 끝나면 고객에게 만족도 평가(별점)를 받는다.

이 시스템은 **정적 홈페이지와 별개의 애플리케이션**이다. 홈페이지 자체는 여전히 빌드 도구 없는
순수 HTML/CSS/JS이고, 상담 채팅만 별도의 서버(API)와 별도의 관리자 화면(Admin)을 둔다.

### 구성 요소 4가지

| 구성 요소 | 경로 | 역할 | 기술 |
|---|---|---|---|
| 정적 홈페이지 | `/`, `stemcell/`, `korea-travel/` | 고객이 보는 페이지. 상담 위젯이 우측 하단에 뜬다 | HTML/CSS/JS (빌드 없음) |
| 채팅 위젯 | `js/chat/` | 홈페이지에 삽입되는 채팅 UI. ES 모듈 9개로 구성 | Vanilla JS (ES Module) |
| API 서버 | `apps/api` | 채팅방·메시지 저장, AI 응답, 번역, 인증, 운영 지표 | Express + Socket.IO + Prisma |
| 관리자 화면 | `apps/admin` | 운영자가 로그인해서 상담을 처리하는 화면 | Next.js |
| 공용 타입 | `packages/shared` | API와 관리자 화면이 함께 쓰는 타입·상수 (상태값, 언어코드 등) | TypeScript |

세 워크스페이스(`apps/api`, `apps/admin`, `packages/shared`)는 루트의 `npm workspace`로 묶여 있다.
정적 홈페이지는 이 workspace에 속하지 않는다 — 여전히 빌드 없이 파일을 그대로 서비스한다.

### 요청이 흘러가는 순서 (고객이 메시지를 보낼 때)

```
고객 브라우저 (js/chat/widget.js)
   │  1) Socket.IO 연결 시도, 실패하면 3초 폴링으로 자동 전환
   ▼
apps/api (Express + Socket.IO)
   │  2) 메시지를 DB에 저장 (Message 테이블)
   │  3) Socket.IO로 관리자 화면에 즉시 브로드캐스트
   │  4) 번역 파이프라인을 백그라운드로 실행 (trackBackground)
   │  5) 봇 응답이 필요하면 AI 파이프라인 실행 (역시 백그라운드)
   ▼
PostgreSQL (chat_rooms, messages, customers, ...)
   ▲
   │  관리자 화면도 같은 API를 통해 Socket.IO/REST로 읽고 쓴다
apps/admin (운영자 브라우저)
```

핵심 원칙: **메시지를 저장하는 함수는 단 하나**다(HTTP 라우트든 소켓 이벤트든 같은 저장 함수를
거친다). 저장에 성공한 뒤에만 실시간으로 알린다. 이 원칙을 깨고 "일단 화면에 보여주고 나중에
저장"하는 식으로 바꾸면 저장 실패 시 화면과 DB가 어긋난다.

## 3. 로컬 개발 환경 준비 (처음 한 번)

### 3-1. 필요한 프로그램 설치

1. **Node.js 22 LTS** — `node -v` 로 확인. 22 미만이면 일부 API(`loadEnvFile` 등)가 없어서 동작하지
   않는다.
2. **Docker Desktop** — PostgreSQL을 컨테이너로 띄우는 데 쓴다. 로컬에 Postgres를 직접 설치해도
   되지만, 팀 전체가 같은 버전을 쓰기 위해 Docker를 권장한다.

### 3-2. 저장소 준비

```bash
git clone <저장소>
cd stemcarejapan-website
npm install                        # workspace 전체 의존성 설치
cp .env.example .env                # 아래 4장에서 각 값을 설명한다
npm run build -w packages/shared    # 반드시 먼저 빌드한다 (아래 "자주 하는 실수" 참고)
docker compose up -d postgres       # DB 컨테이너 기동
npm run db:generate -w apps/api     # Prisma 클라이언트 생성
npm run db:migrate:deploy -w apps/api  # 스키마 적용
npm run db:seed -w apps/api         # 초기 운영자 계정 생성
```

`packages/shared`를 먼저 빌드해야 하는 이유: 이 패키지는 CommonJS로 컴파일되어
`dist/index.js`를 만든다. `package.json`의 `main` 필드가 그 파일을 가리키므로, 빌드 전에는
`apps/api`와 `apps/admin`이 `@stemcare/shared`를 아예 찾지 못한다. `Cannot find module
'@stemcare/shared'` 오류가 나면 십중팔구 이 단계를 건너뛴 것이다.

### 3-3. 이 프로젝트만의 포트 배치

이 개발 머신에서는 5432(Postgres 기본 포트)와 3000(Next.js 기본 포트)을 다른 프로젝트가 쓰고
있어서, 계획서의 기본값과 다르게 조정했다. **새 환경에서 세팅할 때도 이 값을 그대로 따를 필요는
없다** — `.env`와 `docker-compose.yml`만 일치시키면 된다.

| 서비스 | 로컬 개발 주소 | E2E 테스트 전용 주소 |
|---|---|---|
| 정적 홈페이지 | http://localhost:8080 | http://127.0.0.1:18081 |
| API 서버 | http://localhost:4000 | http://127.0.0.1:14001 |
| 관리자 화면 | http://localhost:3100 | http://127.0.0.1:13101 |
| PostgreSQL | localhost:5434 (컨테이너 내부는 5432) | 같은 DB, `TEST_DATABASE_URL`로 구분 |

E2E가 별도 포트를 쓰는 이유: 개발자가 `npm run dev:api` 등을 켜 둔 상태에서도 `npm run test:e2e`를
동시에 돌릴 수 있게 하기 위해서다. E2E는 자체적으로 서버 3개를 띄우고 끝나면 종료한다.

### 3-4. 매일 개발할 때

터미널 3개를 연다.

```bash
# 1: 정적 홈페이지
docker compose up -d web

# 2: API 서버 (파일 변경 시 자동 재시작)
npm run dev:api

# 3: 관리자 화면
npm run dev:admin
```

관리자 초기 계정은 `.env`의 `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD`로 정한다. 값을 지정하지
않으면 시드 스크립트가 개발용 기본값을 쓴다 — **운영 배포에는 반드시 직접 값을 지정해야 한다**
(9장 참고). 시드를 다시 실행해도 기존 계정의 비밀번호는 바뀌지 않는다.

## 4. 환경변수 레퍼런스

전부 루트의 `.env` 파일 하나에 모여 있다 (`apps/api`와 `apps/admin` 모두 이 파일을 읽는다).
`apps/api/src/config.ts`가 실제로 읽는 코드다.

| 변수 | 기본값(개발) | 설명 |
|---|---|---|
| `NODE_ENV` | `development` | `production`이면 `assertProductionConfig()`가 아래 항목들을 검증하고, 문제가 있으면 **서버가 아예 기동하지 않는다** |
| `API_PORT` | `4000` | API 서버 포트 |
| `DATABASE_URL` | `postgresql://stemcare:stemcare@localhost:5434/stemcare_chat` | 운영 DB 접속 문자열 |
| `TEST_DATABASE_URL` | (필수, 개발 DB와 이름이 달라야 함) | 자동 테스트 전용 DB. 이름이 `_test`로 끝나야 하고 개발 DB와 달라야 한다 — 실수로 개발 데이터를 지우는 사고를 막기 위한 코드 상의 강제 검사다 |
| `JWT_SECRET` | `dev-only-secret` (개발 전용) | 운영자 로그인 세션 서명 키. 운영 환경에서는 32자 이상이어야 하고 기본값이면 서버가 거부한다 |
| `ADMIN_COOKIE_NAME` | `scj_admin_token` | 운영자 인증 쿠키 이름 |
| `OPENAI_API_KEY` | (비움) | AI 상담봇·번역·요약에 사용. **자동 테스트는 이 값을 강제로 비운다** — 테스트가 외부 API에 의존하면 네트워크가 없거나 키가 없는 환경(CI 등)에서 실패하기 때문이다 |
| `AI_MODEL` / `TRANSLATION_MODEL` | `gpt-5-mini` | 사용할 모델 이름 |
| `WEBSITE_ORIGIN` | `http://localhost:8080` | CORS 허용 출처(고객 위젯). 운영에서는 `https://` 로 시작하는 origin이어야 한다 |
| `ADMIN_ORIGIN` | `http://localhost:3100` | CORS 허용 출처(관리자 화면). 운영에서는 `https://` 로 시작하는 origin이어야 한다 |
| `NEXT_PUBLIC_API_URL` | `http://localhost:4000` | 관리자 화면이 API를 호출할 주소. **Next.js 빌드 시점에 값이 고정된다** — 컨테이너 실행 중에 바꿔도 반영되지 않는다. 바꾸려면 다시 빌드해야 한다 |
| `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` | — | 시드 스크립트가 만드는 초기 운영자 계정. 운영에서는 필수이며, 12자 미만이거나 기본값이면 시드가 거부한다 |
| `RATE_LIMIT_LOGIN` / `RATE_LIMIT_CHAT_START` | (프로덕션 기본값 있음) | 로그인·상담시작 요청 제한 횟수. 테스트 환경에서는 자동으로 넉넉한 값을 쓴다 |

### 운영 환경 전용 검증

`assertProductionConfig()`(`apps/api/src/config.ts`)는 `NODE_ENV=production`일 때만 동작하며,
아래 중 하나라도 문제가 있으면 에러를 던져 **서버 기동을 막는다**.

- `JWT_SECRET`이 32자 미만이거나 알려진 기본값 중 하나
- `DATABASE_URL`이 비어 있음
- `WEBSITE_ORIGIN` / `ADMIN_ORIGIN`이 없거나, `https://` 가 아니거나, 경로가 붙어 있음(origin만
  허용 — 예: `https://example.com`은 되지만 `https://example.com/`는 안 됨)

"설정을 깜빡했다"가 보안 사고로 이어지는 걸 막으려는 의도적인 설계다. 운영 배포 중 서버가 안
뜨면 가장 먼저 이 함수가 뭐라고 하는지 로그를 본다.

## 5. 데이터 모델 개요

PostgreSQL 테이블 7개 (Prisma 스키마: `apps/api/prisma/schema.prisma`).

| 테이블 | 핵심 필드 | 설명 |
|---|---|---|
| `Operator` | email, passwordHash, role | 운영자 계정. `role`은 `admin` 또는 `operator` |
| `Customer` | name, phone, email, preferredLanguage, pseudonymizedAt | 상담 고객. `pseudonymizedAt`은 개인정보 보관 정책(6장)이 채운다 |
| `ChatRoom` | status, assignedOperatorId, visitorTokenHash, closedAt | 상담방 하나. `status`는 `bot` → `waiting` → `active` → `closed` 순서로 흐른다 (역행 가능) |
| `Message` | senderType, originalText, translatedText, visibleText, translationStatus | 메시지 한 건. 원문과 번역문을 함께 보관한다 |
| `ChatSummary` | summary, customerNeeds, nextAction, riskFlags | AI가 만든 상담 요약. 운영자에게 인계할 때 참고 자료 |
| `OperatorNote` | note | 운영자가 남기는 내부 메모. **고객에게는 절대 노출되지 않는다** |
| `ChatFeedback` | rating(1~5), comment | 상담 종료 후 고객 만족도 평가. 상담방 하나당 1건만 가능 |

`visitorTokenHash`가 왜 필요한가: 고객은 로그인하지 않는다. 상담 시작 시 발급받은
`visitorToken`(64자 hex)을 `X-Visitor-Token` 헤더에 실어 보내야 자기 상담방임을 증명한다. 서버는
평문 토큰을 저장하지 않고 SHA-256 해시만 저장한다 — DB가 유출돼도 토큰 자체는 복원할 수 없다.

`Message.visibleText`가 왜 따로 있는가: 발신자 관점(원문)과 수신자 관점(번역문)이 다르기 때문에,
"이 메시지를 지금 누구에게 보여줘야 하는가"를 매번 계산하지 않고 미리 결정해 저장해 둔다.

## 6. 개인정보 보관 정책 (Retention)

법적/윤리적 요구사항: "불필요한 개인정보를 오래 보관하지 않는다."

| 시점 | 동작 | 코드 |
|---|---|---|
| 상담 종료(모든 상담방이 `closed`) 후 180일 | 고객의 이름·전화·이메일·메모를 비식별화(`고객_xxxx`, `[삭제됨]`, `null`) | `pseudonymizeOldCustomers` |
| 상담방 종료 후 365일 | 그 상담방의 메시지·요약·메모·평가를 완전히 삭제 | `deleteOldMessages` |

둘 다 `apps/api/src/ops/retention.ts`에 있고, 상수(`PSEUDONYMIZE_AFTER_DAYS=180`,
`DELETE_MESSAGES_AFTER_DAYS=365`)로 코드에 명시되어 있다. **날짜만 바꾸면 정책이 바뀐다** — 별도
설정 화면은 없다.

- 자동 실행: `apps/api/src/ops/retentionJob.ts`가 매일 한국 시각 새벽 4시(`0 4 * * *`, `node-cron`)에
  실행한다. 서버 로그에 `retention_job_scheduled`(기동 시), `retention_job_completed`(실행 후)가
  찍힌다.
- 수동 실행: `npm run ops:retention -w apps/api`
- 주의: 180일 비식별화는 **연락처만** 지운다. 상담 대화 본문 자체를 익명화하는 기능이 아니다 —
  대화 내용은 365일 규칙으로만 삭제된다.
- `pseudonymizeOldCustomers`는 `every: { status: 'closed', ... }` + `some: {}` 조건을 함께 쓴다.
  `every`만 쓰면 상담방이 하나도 없는 고객(빈 배열)도 조건을 만족해버린다(공집합에 대해 `every`는
  항상 참) — `some: {}`로 "상담방이 최소 1개는 있어야 한다"를 강제해 이 빈틈을 막는다.

## 7. 테스트

| 목적 | 명령 | 비고 |
|---|---|---|
| API 단위/통합 테스트 | `npm run test -w apps/api` | 실행 전 `pretest`가 `TEST_DATABASE_URL`에 스키마를 자동으로 push한다 |
| 관리자 화면 테스트 | `npm run test -w apps/admin` (`npm run test:admin`) | Vitest + Testing Library |
| 위젯 테스트 | `npm run test:widget` | 브라우저 없이 DOM만 흉내 내서 검증 |
| E2E (전체 흐름) | `npm run test:e2e` | Playwright. PostgreSQL만 사전 실행하면 나머지(홈페이지·API·관리자)는 자동으로 뜨고 끝나면 종료된다 |
| E2E를 눈으로 보며 디버깅 | `npm run test:e2e:ui` | Playwright UI 모드 |
| 백업 스크립트 회귀 검증 | `python3 tests/ops/test_backup_scripts.py` | 손상된 백업/복구 실패 경로를 시뮬레이션 |

### 테스트 DB가 안전하게 분리되는 원리

- `apps/api/vitest.setup.ts`가 모든 테스트 파일이 로드되기 **전에** `process.env.DATABASE_URL`을
  `TEST_DATABASE_URL` 값으로 덮어쓴다.
- `apps/api/scripts/test-db-url.cjs`의 `testDatabaseUrl()`이 그 값을 검증한다: DB 이름이 `_test`로
  끝나야 하고, 개발 DB와 달라야 한다. 어기면 테스트 자체가 즉시 실패한다 — **실수로 개발 DB를
  밀어버리는 사고를 코드 레벨에서 막는 장치**다.
- `pretest` 훅(`db:push:test`)이 테스트 실행 전 그 DB에 스키마를 자동으로 맞춘다.

### vitest 버전을 API/Admin에서 다르게 올리면 안 되는 이유

`apps/admin`의 vitest는 `apps/api`와 **같은 메이저 버전**을 유지해야 한다. 버전이 갈리면
`@testing-library/jest-dom`이 실행 중이 아닌 쪽의 `expect`를 확장하게 되어, 그쪽 워크스페이스의
매처(`toBeInTheDocument()` 등)가 전부 깨진다. 한쪽만 업그레이드하고 넘어가면 나중에 원인을 찾기
매우 어렵다.

### AI 관련 테스트

자동 테스트는 `OPENAI_API_KEY`를 항상 비운다. AI 호출이 실패하는 경로(실패 시 자동으로 운영자
대기로 전환되는 동작 등)까지 테스트로 검증하며, **실제 AI 응답 품질은 자동 테스트 범위 밖**이다.
품질 확인은 사람이 직접 브라우저로 확인해야 한다.

## 8. 실시간 통신 (Socket.IO)과 폴백

- 고객 위젯과 관리자 화면 모두 우선 Socket.IO로 연결한다. CDN이 차단되거나 방화벽 때문에
  실패하면 **자동으로 폴링으로 전환**된다(위젯 3초, 관리자 상세 3초, 목록 5초). 화면을 만드는
  쪽에서는 어느 방식으로 동작 중인지 신경 쓸 필요가 없다 — `js/chat/stream.js`가 그 전환을
  책임진다.
- 소켓이 살아있어도 폴링은 안전망으로 계속 돈다. 서버 부담보다 "화면이 실제 상태와 어긋나는 것"이
  더 비싼 대가라고 보기 때문이다.
- 탭이 백그라운드면 폴링을 쉰다. 다른 창을 보다가 돌아오면 한 박자 뒤에 갱신된다 — 버그가
  아니다.
- 소켓 인증 순서에 주의: **`auth.roomId` + `visitorToken`(고객)이 쿠키보다 먼저 확인된다.**
  브라우저 쿠키는 포트를 구분하지 않기 때문에, 운영자로 로그인해 둔 브라우저로 고객 위젯(다른
  포트)을 열면 그 소켓 연결에도 운영자 쿠키가 함께 실린다. `roomId`/`visitorToken`이 있으면
  쿠키가 뭐든 고객으로 인증해야 한다 — 이 순서를 코드에서 바꾸면 안 된다.

## 9. 배포

**요약이며, 실제 배포는 반드시 [`deploy/DEPLOY.md`](../../deploy/DEPLOY.md)를 그대로 따른다.**
아래는 처음 보는 사람이 전체 흐름을 이해하기 위한 설명이다.

1. 서버에 Docker/Docker Compose 설치, 도메인 DNS를 서버 IP로 연결.
2. `deploy/.env.prod.example`을 `.env`로 복사하고 값을 채운다 (비밀번호·`JWT_SECRET`은
   `openssl rand`로 생성).
3. **HTTPS 인증서는 최초 발급 시 "닭과 달걀" 문제가 있다**: nginx는 인증서가 있어야 HTTPS로 뜨는데,
   인증서(Let's Encrypt certbot)는 도메인이 응답해야 발급된다. 그래서 최초 1회는
   `docker-compose.bootstrap.yml`로 HTTP 전용 nginx를 잠깐 띄워 인증서만 발급받고, 이후 일반
   구성으로 전환한다. 갱신은 `deploy/renew-certificates.sh`를 호스트 스케줄러(cron 등)에 12시간
   주기로 등록해 자동화한다.
4. `docker compose -f docker-compose.prod.yml up -d --build`로 전체 기동. DB 마이그레이션은 API
   컨테이너가 시작될 때 자동 적용된다.
5. 관리자 계정 시드 (`SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD` 필수, 12자 미만이거나 기본값이면
   거부됨).
6. 배포 전 반드시 [`CHECKLIST.md`](../../CHECKLIST.md)의 모든 항목을 통과해야 한다.

### 이미지 빌드에서 흔히 놓치는 것

- `prisma`와 `tsx`는 devDependencies라서, 운영 이미지의 `--omit=dev` 설치 단계에서 빠진다. 하지만
  마이그레이션 적용과 시드 실행에는 **런타임에** 이 CLI들이 필요하다. `deploy/Dockerfile.api`는
  정확한 버전을 고정해 런타임 스테이지에 별도로 설치한다 — 버전을 바꾸면 이 부분도 같이 맞춰야
  한다.
- `NEXT_PUBLIC_API_URL`과 `basePath`(`/admin`)는 Next.js 빌드 시점에 고정된다. 컨테이너 실행 중
  환경변수를 바꿔도 반영되지 않는다 — 값을 바꾸려면 이미지를 다시 빌드해야 한다.

### 롤백

```bash
git checkout <이전-커밋>
docker compose -f docker-compose.prod.yml up -d --build
```

**DB 마이그레이션은 자동으로 되돌아가지 않는다.** 컬럼을 삭제하는 마이그레이션을 배포한 뒤
롤백하려면 백업에서 복구해야 한다. 그래서 컬럼 삭제는 항상 "코드에서 사용 중단 → 며칠 관찰 →
다음 배포에서 삭제" 순서로 나눠서 진행한다.

## 10. 백업과 복구

- `deploy/backup/backup.sh`가 `backup` 컨테이너에서 매일 한국 시각 새벽 3시(+ 컨테이너 시작 시
  1회) PostgreSQL 덤프를 만들어 `/backups`에 **7일치**를 보관한다.
- 복구: `deploy/backup/restore.sh <백업파일>`. 손상된 gzip이나 SQL 오류는 성공으로 보고하지
  않으며, SQL 실행 중 오류가 나면 기존 스키마로 롤백한다(부분 복구 상태로 남기지 않는다).
- **"백업이 있다"와 "복구할 수 있다"는 다르다.** 실제로 복구해 본 적 없는 백업은 없는 것과
  같다. 한 달에 한 번 [`deploy/backup/RESTORE-DRILL.md`](../../deploy/backup/RESTORE-DRILL.md)의
  절차대로 운영 DB를 건드리지 않는 별도 DB(`restore_drill`)에 실제로 복구해 보고, 표에 날짜·결과를
  기록한다.
- 배포 직후에는 "설정했다"가 아니라 "복구해봤다"로 확인한다 — 처음 배포 후 한 번은 반드시
  `restore.sh`를 실제로 실행해서 복구가 되는지 확인한다.

## 12. 로깅과 보안

- 로그는 `pino`로 JSON 한 줄씩 남긴다 (`apps/api/src/common/logger.ts`). **이름·전화·이메일·메모·
  상담 본문(원문/번역문 포함)은 로그에 절대 남지 않는다** — `maskPersonalData()`가 지정된 키를
  재귀적으로 `[REDACTED]`로 바꾸고, HTTP 요청/응답 로그도 `{id, method, url}` / `{statusCode}`만
  기록하도록 serializer 자체를 제한해 둔다. "마스킹을 깜빡해서 새는" 경로를 구조적으로 없앤
  것이다.
- 특정 상담의 실제 내용을 확인해야 하면 로그가 아니라 **권한이 있는 관리자 화면**에서 확인한다.
- 보안 미들웨어: `helmet`, 로그인/상담시작 rate limit(`apps/api/src/common/security.ts`), 운영
  환경 설정 검증(`assertProductionConfig`, 4장 참고).
- 관리자 인증 쿠키는 `HttpOnly; Secure; SameSite=Lax`여야 한다 — 배포 후 개발자도구에서 직접
  확인한다.

## 13. 코드를 고칠 때 꼭 지켜야 하는 규칙

프로젝트 전반에 반복적으로 등장하는, 실수하기 쉬운 규칙들을 모았다.

1. **상태값·언어코드 등 상수는 반드시 `@stemcare/shared`에서 import한다.** 문자열을 직접 쓰지
   않는다 — API와 관리자 화면의 상태값이 어긋나는 사고를 막기 위해서다.
2. **위젯 문구는 전부 `data-i18n` 속성으로 표시한다** (`js/chat/i18n.js`). 한국어/일본어 두 사전은
   반드시 같은 키를 가져야 한다 — 키가 어긋나면 한쪽 언어에서 문구가 원래 키 문자열 그대로
   노출된다. 페이지가 `<html lang>`을 바꾸면 위젯이 MutationObserver로 감지해 같은 언어로 다시
   칠한다.
3. **관리자 화면의 모든 API 호출은 `credentials: 'include'`가 필요하다** (`apps/admin/lib/api.ts`).
   빠뜨리면 인증 쿠키가 전송되지 않아 로그인했는데도 401이 난다.
4. **비동기 백그라운드 작업(번역, AI 응답 등)은 반드시 `trackBackground()`에 등록한다**
   (`apps/api/src/common/background.ts`). 테스트가 끝나기 전, 또는 서버 종료 신호를 받았을 때
   이 작업들을 기다렸다가(`drainBackground`) 안전하게 마무리하기 위해서다. 등록하지 않은
   백그라운드 작업은 테스트 DB가 초기화된 뒤에도 실행되다가 예기치 않은 오류를 낼 수 있다.
   다만 이 큐는 메모리에만 있다 — **프로세스가 중단되면 재개되지 않는다.** 배포 직후에는 운영
   현황의 미응답 지표와 번역 실패 수를 확인한다.
5. **AI 모델 호출 중에는 DB 잠금을 잡지 않는다.** 모델 응답을 기다리는 동안 잠금을 쥐고 있으면
   그 사이 다른 요청이 전부 막힌다. 대신 **응답을 저장하기 직전에 상담 상태와 마지막 메시지를
   다시 확인**한다 — 모델이 응답하는 몇 초 사이에 운영자가 이미 배정됐거나 상담이 종료됐을 수
   있기 때문이다. 방 잠금(`lockRoom`)은 이 짧은 재확인·저장 구간에만 사용한다.
6. **자동 테스트에서 `OPENAI_API_KEY`가 필요하게 만들면 안 된다.** 키가 없어도 모든 테스트가
   통과해야 한다 (AI 실패 시 자동으로 운영자 대기로 전환되는 경로까지 포함해서).
7. **`render.js`는 fetch를 모르고, `api.js`는 DOM을 모른다.** 위젯 레이어를 나눈 이유이며, 이
   경계를 넘나드는 코드를 추가하면 위젯을 서버 사이드 렌더링 등 다른 맥락에 재사용하기 어려워진다.

## 14. 자주 하는 실수와 해결

| 증상 | 원인 | 해결 |
|---|---|---|
| `Cannot find module '@stemcare/shared'` | `packages/shared`를 빌드하지 않음 | `npm run build -w packages/shared` |
| 포트가 이미 사용 중 | 다른 프로세스가 같은 포트 점유 | `lsof -i :4000` 으로 확인 후 종료 |
| 관리자 화면에서 CORS 오류 | `.env`의 `ADMIN_ORIGIN`이 실제 접속 주소와 다름 | 값을 맞추고 API 서버 재시작 |
| DB 연결 안 됨 | postgres 컨테이너가 `healthy`가 아니거나 포트 불일치 | `docker compose ps` 확인, `DATABASE_URL` 포트(5434) 확인 |
| 테스트가 개발 DB를 건드릴까 걱정된다 | 걱정할 필요 없음 — 코드가 강제로 막는다 | `TEST_DATABASE_URL` 이름이 `_test`로 끝나고 개발 DB와 다르면 안전 (7장 참고) |
| `NEXT_PUBLIC_API_URL`을 바꿨는데 반영 안 됨 | Next.js는 빌드 시점에 값을 고정함 | 개발 서버 재시작 / 운영은 이미지 재빌드 |
| 로그에서 고객 이름을 검색해도 안 나옴 | 의도된 동작 (12장) | 관리자 화면에서 확인 |
| 배포 후 관리자 화면이 이상한 곳에 뜸 (basePath) | 이미지 빌드 시 `NEXT_BASE_PATH`를 안 넘김 | `deploy/Dockerfile.admin`의 `ARG` 확인 후 재빌드 |
