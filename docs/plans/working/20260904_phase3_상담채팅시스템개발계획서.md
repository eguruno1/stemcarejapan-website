# Phase 3: 운영자 관리자 화면 개발계획서 — 완료

작성일: 2026-09-04 · 구현 검토 및 완료일: 2026-09-18

상태: **완료 (현재 고객 식별·REST 범위)**. `feat/consulting-chat-phase3`에서 Phase 2 포함 구현을 검토·수정했다. 로그인·상담 목록·상세·배정·답변·종료·메모·설정·동일 고객 레코드의 상담 이력과 스크롤을 검증했다.

[검토 전 원문](../history/20260918_phase2-3_review/20260904_phase3_상담채팅시스템개발계획서.md)은 이력으로 보존한다. 현재 구현 기준은 아래 내용과 실제 소스이며 API 계약은 [API 문서](../../../apps/api/API.md)를 따른다. 이 완료 판정은 브랜치 검토 범위이며 master 병합·원격 push·배포를 의미하지 않는다.

## 실제 구현과 초안의 차이

| 항목 | 현재 기준 |
|---|---|
| UI 구성 | Next.js 15 App Router + React 18. 공통 globals.css와 컴포넌트 inline style 사용. 초안의 CSS Modules 표현 정정. shadcn/ui는 사용하지 않음. |
| 폴링 | 목록 5초 / 선택한 방 상세 3초. 모든 화면이 5초라는 초안 설명 정정. 숨겨진 탭에서는 주기 조회 생략. |
| 인증 | 모든 요청 credentials: include. 401을 API 클라이언트에서 인증 컨텍스트로 전달. 비활성 계정의 기존 세션도 화면에서 해제. |
| 상세 상태 | 이전 방·이전 필터·쓰기 이전 조회 결과를 무시. 메모는 방 전체의 과거 사본이 아닌 appendNote로 현재 상태에 추가. |
| 전송 | 원문·작성 언어·clientMessageId 전송. 실패 후 같은 본문·언어 재시도는 동일 ID 사용. |
| 스크롤 | 갱신 후 높이로 판단하던 코드를 변경해 갱신 전 사용자 위치 사용. ResizeObserver로 같은 개수의 메시지 높이 변경도 보정. |
| 이전 상담 | 동일 customerId의 다른 방 최대 20개. 이름·전화번호가 같다는 이유로 서로 다른 고객 레코드를 자동 연결하지 않음. |
| 테스트 | 기존 관리자 테스트 18개에서 31개로 확대. 위젯 단위 6개와 관리자 E2E 3개 추가. |

## Task 8: 고객별 이전 상담 이력 — 완료 (동일 customerId 범위)

- [x] `CustomerHistoryItem` shared DTO, `listCustomerHistory`, 보호 API 및 클라이언트 연결.
- [x] 현재 방 제외 / 다른 고객 제외 / 최신순 최대 20개 / 메시지 수 / 이력 없음 / 없는 방 / 인증 검사.
- [x] 이력 클릭 시 해당 상담방 이동.
- [x] 조회 실패를 “첫 상담”으로 잘못 표시하지 않고 오류 안내.

**식별 범위 정정:** 공개 상담 시작 API는 매번 새 customerId를 생성한다. 따라서 “같은 사람이 재방문하면 자동으로 예전 상담이 보인다”는 초안의 기대는 현재 구현 범위와 다르다. 이 단계는 **동일 고객 레코드에 연결된 방의 이력 조회**로 완료한다. 전화번호만으로 레코드를 자동 병합하면 다른 사람의 상담을 연결할 수 있으므로 이번 검토에서 임의 병합을 추가하지 않았다. 재방문 인증·동일 고객 연결 기능은 별도의 후속 작업이다.

## 검토에서 수정한 주요 결함

1. 관리자 인증이 만료되어도 이미 표시된 개인정보 화면이 유지되던 문제.
2. 이전 방·이전 필터 요청 결과가 현재 상태를 덮어쓰던 문제.
3. 진행 중 폴링·메모 저장이 방금 받은 메시지를 화면에서 지우던 문제.
4. 갱신 후 높이로 스크롤을 판정해 과거를 읽던 위치가 이동하던 문제.
5. 한국어·일본어 IME 확정 Enter가 전송으로 처리되던 문제.
6. 전송 응답을 잃고 재시도할 때 중복 메시지가 저장될 수 있던 문제.
7. 로그아웃·이력 조회 실패를 성공·첫 상담으로 오인시키던 문제.

## 후속 인계

Phase 4는 현재 폴링을 Socket.IO로 교체하되 방 ID·요청 세대·쓰기 후 오래된 조회 무시·세션 무효화 규칙을 유지한다. Phase 5의 번역문 도착으로 메시지 높이가 바뀌어도 앵커를 유지해야 한다. 재방문 고객 식별·연결과 실제 API 호스팅은 이번 단계의 완료 범위 밖이다. Phase 4~6은 미완료로 유지한다.
