## 로컬 번역·고객 선택 1:1 상담 (2026-09-20)

운영자 **설정 → 상담·번역 설정**에서 번역 제공자를 외부 API 또는 로컬 Ollama로 선택하고 저장한다. 모든 운영자가 공유하며 DB에 저장된다. 연결 확인 버튼은 선택한 제공자로 고정 예제만 번역한다.

```bash
# Ollama가 실행 중이고 qwen3:8b 모델이 설치되어 있어야 한다.
ollama list
# 설치되지 않은 환경에서만 실행
ollama pull qwen3:8b
npm run db:generate -w apps/api
npm run db:migrate:deploy -w apps/api
npm run ops:check-ollama -w apps/api
```

API 서버의 기본 접속 주소는 `http://127.0.0.1:11434`, 모델은 `qwen3:8b`, 요청 제한 시간은 120초다. `.env`의 `OLLAMA_BASE_URL`, `OLLAMA_MODEL`, `OLLAMA_TIMEOUT_MS`로 변경하며 API 서버를 재시작한다. 로컬 번역 실패 시 외부 API로 자동 전환하지 않는다. 고객→운영자 자동 번역과 운영자 번역 미리보기 모두 선택한 제공자를 사용한다. 날짜·금액 등은 미리보기에서 확인한다.

고객은 시작 폼에서 다음 중 선택한다.

- **AI·번역 지원 상담**: 기존 흐름을 유지하며 운영자 설정의 AI 응답·요약 및 자동 번역 스위치를 따른다.
- **담당자 1:1 상담**: 즉시 대기 접수하고 AI 자동 응답·요약 없이 담당자가 직접 대화한다. 기본은 원문 전송이며 운영자가 상담방의 **이 상담 상호 번역 사용**을 켜면 고객 일본어→한국어 표시, 운영자 한국어→고객 선호 언어 미리보기·수정 후 전송을 사용할 수 있다. 방별 번역 설정은 새로고침·상담 재개 후에도 유지된다.

번역 제공자 설정은 AI 상담 모델을 바꾸지 않는다. **AI 응답·요약은 기존 외부 API를 사용한다.** 외부 AI 없이 번역만 쓰려면 로컬 번역을 선택하고 AI 응답·요약 스위치를 끈다. AI를 끄면 기존 bot 상담도 waiting으로 전환되며, 다시 켜도 대기/진행 중인 방에 AI가 재개입하지 않는다. 기존 진행 중 요청은 이미 해당 제공자에 전달됐을 수 있으며 설정 변경 이후 도착한 결과는 폐기한다.

검증(2026-09-20): API 248개·관리자 52개·위젯 17개·일반 Chromium E2E 30개 통과, 전체 빌드 성공. Ollama 라이브 E2E 1개도 별도 실행해 통과했다(일반 실행에서는 건너뜀). 실제 Ollama 브라우저에서 일본어 고객 문의의 한국어 표시와 한국어 답변의 일본어 미리보기·수정·전송을 확인했다. 실제 로컬 한일 예제 번역은 약 2.7~3.4초였으며 모든 문장의 품질 보장을 뜻하지 않는다.

대화창의 **대화 표시**는 원문+번역 / 원문만 / 번역 우선 중 선택한다. 저장된 원문은 유지되고 번역이 없으면 원문을 표시한다. 번역을 켜면 최근 미번역 고객 메시지 20개도 처리하며, 이전 메시지는 「한국어로 번역」으로 요청할 수 있다. 상호 번역을 꺼도 이미 저장된 번역은 삭제하지 않는다. 전체 설정의 자동 번역 허용이 꺼져 있으면 방별 선택을 켜도 모델을 호출하지 않는다.

실제 Ollama 브라우저 검증은 `SCJ_LIVE_OLLAMA=1 npm run test:e2e -- tests/e2e/ollama-live.spec.ts`로 별도 실행한다. 기본 E2E에서는 이 라이브 검증을 건너뛴다.

Docker의 `127.0.0.1`은 컨테이너 자신이다. Docker Desktop에서 호스트 Ollama에 연결하려면 `http://host.docker.internal:11434`를 사용한다. Linux는 접근 가능한 별도 주소/네트워크를 구성해야 한다. Ollama 포트를 공개 인터넷에 노출하지 않는다.

## 관리자 화면 사용법

주소: http://localhost:3100

초기 계정은 `npm run db:seed -w apps/api` 로 만든다.
개발용 기본값은 `admin@stemcarejapan.local` / `change-me-1234`이며,
`.env`의 `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`로 지정할 수 있다. 운영 환경에서는 기본 비밀번호를 거절하므로 명시적인 이메일과 12자 이상의 비밀번호가 필요하다. 기존 계정의 비밀번호는 seed 재실행만으로 바뀌지 않으며, 재설정하려면 `SEED_RESET_PASSWORD=true`를 명시한다.

화면 구성:
- 왼쪽: 상담 목록 (상태 필터 / 정렬 / 읽지 않은 개수)
- 가운데: 메시지 (원문 + 번역문 동시 표시)
- 오른쪽: 상담 상태 조작, 고객 정보, 이전 상담 이력, AI 요약, 내부 메모
- 우상단 `설정`: 로그인한 운영자 정보 확인과 로그아웃
- `/chats/ops`: 상담 상태·미응답·번역 실패·소켓 연결·만족도 운영 지표

메시지·상태 변경은 Socket.IO 로 실시간 반영된다(연결 시 헤더에 `실시간 연결됨`).
소켓이 막힌 환경(방화벽 등)에서는 3초 폴링(목록은 5초)으로 조용히 대체된다.
소켓이 살아 있어도 이 폴링은 안전망으로 계속 돈다 — 서버 부담보다 "안 맞는 화면"이 더 비싸다.
탭이 백그라운드면 폴링을 쉬므로, 다른 창을 보고 있다가 돌아오면 한 박자 뒤에 갱신된다.

## 문제가 생겼을 때

**포트가 이미 사용 중이라고 나온다**
`lsof -i :4000` 으로 누가 쓰는지 확인하고 종료한다.

**관리자 화면에서 CORS 오류가 난다**
`.env` 의 `ADMIN_ORIGIN` 이 `http://localhost:3100` 인지 확인하고 API 서버를 재시작한다.

**DB에 연결이 안 된다**
`docker compose ps` 로 postgres 가 `healthy` 인지 확인한다.
`DATABASE_URL` 의 포트가 5434 인지도 확인한다.

**개발 서버 실행 중 관리자 빌드 후 화면이 깨진다**
일반 개발 서버와 프로덕션 빌드는 `.next/`를 공유한다. 관리자 개발 서버를 종료한 뒤 빌드하고 다시 시작한다. E2E는 별도 `.next-e2e/`를 사용한다.

**`@stemcare/shared` 를 못 찾는다**
`npm run build -w packages/shared` 를 실행한다. `package.json` 의 `main` 이
`dist/index.js` 를 가리키므로 빌드 전에는 찾지 못한다.

## Phase 0·1 검토 완료 (2026-09-18)

- Node.js 22, 홈페이지 8080 / API 4000 / 관리자 3100 / PostgreSQL 5434를 사용한다.
- 관리자도 루트 `.env`를 읽는다. `NEXT_PUBLIC_API_URL` 변경 후 개발 서버를 재시작하고 배포용 빌드는 다시 생성한다.
- API·shared는 CommonJS이며 관리자 앱은 Next.js의 `module: esnext`, `moduleResolution: bundler` 설정을 유지한다.
- `npm test`는 별도 테스트 DB만 초기화한다. `TEST_DATABASE_URL`은 필수이며 DB 이름은 `_test`로 끝나고 개발 DB와 달라야 한다. 직접 Vitest를 실행해도 같은 검사가 적용된다.
- Phase 0 당시 관리자는 API 연결 확인 화면이었다. 현재는 고객 위젯·관리자 업무 화면·Socket.IO·번역/AI·운영 기능까지 구현되어 있다.
- 초기 관리자 비밀번호 변경 UI는 아직 없다. 운영용 초기 계정은 seed 전에 `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`를 지정한다. seed 재실행은 기존 계정의 비밀번호를 바꾸지 않는다.
- 완료 내역과 검증 근거는 `docs/plans/working/`의 단계별 문서에 기록한다. `docs/`는 기본 제외하되 완료 계획서와 검토 이력은 추적하며, Phase 4~6 문서에는 `.gitignore` 예외를 적용했다.

## Phase 2·3 검토 반영 (2026-09-18)

- `/`, `/stemcell/`, `/korea-travel/` 모두 상담 시작 폼을 제공한다. 서비스 페이지는 해당 분야를 미리 선택한다.
- Phase 4 이후 위젯은 소켓 우선이며 연결 실패 시 3초 폴링으로 대체한다. 관리자 상세 3초·목록 5초 폴링은 소켓과 병행하는 안전망이다. 네트워크 왕복·백그라운드 탭·서버 오류 때문에 실제 표시까지 정확히 3초를 보장하지는 않는다.
- 일시적인 서버 오류는 고객 세션을 유지한 채 재연결한다. 401/403/404일 때만 세션 만료로 처리한다.
- 고객·관리자 모두 IME 입력 확정 Enter를 전송으로 취급하지 않는다. 관리자 전송 실패 후 같은 본문·언어로 재시도하면 같은 메시지 ID를 사용한다.
- 자동 스크롤은 갱신 전 맨 아래 100px 이내일 때만 한다. 이전 내용을 읽는 중에는 직접 전송·패널 재열기도 위치를 유지하며, 새 메시지 버튼으로 최신 위치에 이동한다.
- 관리자 API의 401은 인증 상태를 해제한다. 로그아웃 요청 실패는 오류로 표시하며 성공했다고 가장하지 않는다.
- 이전 상담은 **동일 customerId**의 다른 방 최대 20건이다. 현재 공개 상담 시작은 새 customerId를 생성하므로 이름·연락처가 같다고 자동으로 묶지 않는다. 안전한 재방문 고객 식별·연결은 별도 후속 설계가 필요하다.
- 담당자 연결 버튼은 전용 인계 API/소켓 이벤트를 통해 waiting으로 전환한다. waiting/active/closed에서는 AI가 자동 개입하지 않는다.
- 설정 화면은 계정 확인·로그아웃을 제공한다. Phase 5에서 고객 메시지 자동 번역과 인계 요약 생성, 운영자 번역 미리보기·수정 후 전송을 추가했다.

## Phase 4: 실시간 채팅 — 완료 (2026-09-18)

- 고객 위젯·관리자 화면 모두 Socket.IO 로 연결한다. 실패(CDN 차단, 방화벽 등)하면
  자동으로 폴링으로 대체되고, 화면은 어느 쪽으로 동작하는지 신경 쓸 필요가 없다.
- 소켓 이벤트는 `chat:` 접두어(메시지·입력중·핸드오프), 목록 갱신은 `rooms:` 접두어를 쓴다.
  자세한 이벤트 목록은 `apps/api/API.md` 참고.
- **소켓 인증은 auth.roomId+visitorToken(고객)을 쿠키보다 먼저 확인한다.** 브라우저 쿠키는
  포트를 구분하지 않으므로, 운영자로 로그인해 둔 브라우저로 고객 위젯(다른 포트)을 열면
  그 소켓 연결에도 운영자 쿠키가 함께 실려 온다. roomId/visitorToken 이 있으면 쿠키가
  뭐가 와 있든 고객으로 인증해야 한다 — 순서를 바꾸면 안 된다.
- 메시지 저장 로직은 여전히 `createMessageRow` 한 곳뿐이다. HTTP 라우트와 소켓 핸들러가
  같은 함수를 부르고, 저장 성공 후에만 브로드캐스트한다.
- 운영자가 방을 열어(소켓으로 그 방에 join 한) 있는 동안 온 고객 메시지는 unread 로
  쌓이지 않는다. 접속 상태(담당자 온라인 여부)는 DB에 저장하지 않고 그때그때
  Socket.IO 연결 목록을 세어 계산한다 — 서버가 죽어도 "접속 중"이 영원히 남지 않는다.
- 소켓으로 보낸 메시지가 서버에서 거부되면(방 종료 등) `chat:error` 에 그 메시지의
  `clientMessageId` 가 함께 온다. 없으면 위젯의 "전송 중" 말풍선이 ack(성공)도
  error(실패)도 못 받고 영원히 멈춰 있는다.

## Phase 5: 번역·AI 상담 — 완료 (2026-09-18)

- 고객 메시지는 실제 원문 언어를 감지해 운영자의 읽기 언어인 한국어로 비동기 번역한다. 최초 상담 폼의 문의도 포함하며 실패 시 원문을 유지한다.
- 운영자는 한국어를 기본 작성 언어로 사용하고, 고객 언어로 번역한 문장을 미리보기·수정·재번역한 뒤 전송한다. 상담 종료 시 미리보기에서도 전송을 차단한다.
- 상담 시작 시 API 키 없이도 한일 고정 인사말을 저장한다. 일반 첫 문의는 접수 안내만 제공하고, 민감 문의·운영자 요청은 규칙으로 즉시 waiting 전환한다.
- bot 상태에서 규칙 검사 후 AI 상담을 실행한다. 가격·예약·건강상태 등 전환 대상 또는 AI 실패 시 운영자로 인계하며, 인계 이후에는 자동 답변하지 않는다.
- 최근 대화를 바탕으로 요약·고객 요구·다음 행동·위험 태그를 고객 패널에 표시한다.
- 방별 AI 작업을 순서대로 처리하고 재전송에 따른 중복 실행을 방지한다. 응답 저장 직전 상태와 최신 메시지를 다시 확인해 배정·종료 후 늦은 AI 답변을 폐기한다.
- 번역 8초, 상담·요약 15초 제한과 요청 취소를 적용한다. 백그라운드 작업은 메모리 기반이며 서버 재시작 후 자동 재처리하는 영속 큐는 구현 범위에 포함하지 않는다.

### E2E 실행 환경

`npm run test:e2e`는 shared/API를 빌드하고 테스트용 홈페이지(127.0.0.1:18081), API(14001), 관리자(13101)를 자동 실행·종료한다. 일반 개발 서버를 재사용하지 않는다. 관리자 테스트 산출물은 `.next-e2e/`로 분리한다.

`.env`의 `TEST_DATABASE_URL`이 필요하며 Phase 1과 동일한 안전 검사를 적용한다. 테스트 전용 운영자를 upsert하고 테스트 상담을 이 DB에 생성한다. API 테스트와 같은 DB를 사용하므로 **동시에 실행하지 않는다**. 개발 DB의 seed 계정이나 비밀번호에는 의존하지 않는다. Chromium 설치가 필요하면 `npx playwright install chromium`을 실행한다.

위젯 API 기본 주소는 localhost 환경의 4000 포트, 그 외에는 같은 출처다. 필요할 때 모듈 로드 전에 `window.STEMCARE_CHAT_API_URL`을 설정할 수 있고, E2E는 이를 이용해 테스트 API를 지정한다. 실제 배포에서는 접속 가능한 API와 CORS 설정을 먼저 준비해야 한다.

### 로컬 번역에서 실패 안내만 보이는 경우

운영자 `/settings`에서 **로컬 Ollama (qwen3:8b)**를 선택한 뒤 **설정 저장**을 누른다.
「선택한 제공자 연결 확인」은 예제 문장 테스트일 뿐 설정을 저장하지 않는다.
테스트 DB에서 제공자를 변경해도 실제 개발 DB에는 적용되지 않는다. 초기 제공자는 외부 API이므로
`OPENAI_API_KEY`가 비어 있으면 외부 번역은 실패한다. 자동으로 다른 제공자로 전환하지 않는다.
저장 후 기존 실패 메시지는 「다시 번역」, 작성 중 답변은 「번역 확인」으로 다시 시도한다.
한국어→일본어 답변은 작성 언어가 한국어이고 고객 선호 언어가 일본어여야 한다.
